## Reading the inventory

`D` = capability described in official documentation; `U` = not verified in this assessment, not evidence of absence; `P` = partner/commercial discovery needed. Quality: `aggregate`, `acquisition`, `operational`, `clinical candidate`, `financial candidate`. None means automatically verified identity, newness or reconciled cash. Complexity is relative engineering plus maintenance burden: L/M/H/VH, not a delivery estimate. Priority P1 = candidate for first chosen stack, P2 = subsequent demand-driven adapter, P3 = discovery/defer; P1 does not mean integrate every P1 vendor.

Columns: **Access** includes method/auth and notifications; **Objects/IDs & evidence** states useful data and limits; **History / operations / commercial** addresses backfill, pagination/rates, sandbox and restrictions. `U` items must be resolved in the manifest before production. All rows inherit G's PHI minimization, explicit practice authorization, credential isolation and no automatic advertising uploads. Public documentation does not establish contractual permission to process PHI.

## Selection and verification gates

Choose by actual client stack, stable identifiers, permitted access, authoritative outcome coverage, historical completeness, testability, total maintenance cost and ability to reconcile cash. Prefer one stack with a documented booking-to-PMS patient crosswalk over many disconnected advertising adapters. A second adapter fixture should exercise the same domain without schema changes.

Before implementation estimate: obtain product/edition/version; vendor-approved access path; sample sanitized payloads; signature/auth specification; permissions and BAA review; stable keys; status semantics; historical boundaries and deletion behavior; page/rate/backoff contract; test account/fixtures; exact cost and deprecation policy. An unknown capability blocks only the metric requiring it, not all use of the connection. Publish connection capability/coverage beside reports.

No direct vendor account calls were made. Some official pages could not be retrieved fully, especially Meta; partner-gated or historical documentation is explicitly marked. Numerical quotas are intentionally not generalized across vendors/endpoints. The implemented manifest must record current tested limits and pagination recovery rather than copy a generic number from this assessment.

### Findings that change adapter requirements

NexHealth's documented payment convention is negative for a ledger payment and positive for a refund; its ledger entry alone does not establish money received. One request can generate several source payment components. Normalize positive magnitudes plus explicit canonical kind, preserve component identities and reconcile economic totals. Never use a generic “negative means refund” rule. [NexHealth payment specification](https://docs.nexhealth.com/reference/payments).

Square's payment guide describes location-scoped listing and a default location when omitted. A complete sync must enumerate approved locations rather than equate one successful default-location query with full practice coverage. Completed/captured/provider balance states must be evaluated against F1; no bank-receipt inference from success alone. [Square payment guide](https://developer.squareup.com/docs/payments-api/take-payments).

Search Console uses provider-defined reporting dates, omits some no-data rows and does not guarantee all query rows. Preserve source timezone and coverage; do not manufacture person-level query matches or exact local-day redistribution. [Search Analytics query](https://developers.google.com/webmaster-tools/v1/searchanalytics/query).

Open Dental exposes appointment IDs/status and modification-time filters, but its source “new patient” flag or appointment completion still requires the approved practice history/authority rule. Do not directly map every status to clinical attendance. [Appointments](https://www.opendental.com/site/apiappointments.html).

### Capability-based prioritization

First apply hard gates: permitted access/privacy, stable identities or approved import keys, sufficient authority for the intended fact, retention/replay feasibility and usable test evidence. Then rank passing candidates by actual client adoption, acquisition-to-clinical crosswalk quality, history/completeness, cash reconciliation feasibility, operational maintenance and cost. Unsupported cash need not block an acquisition adapter, but it blocks advertising verified cash from that adapter. Choose one website/form category, one booking/clinical authority and one collection evidence source; optional call adapter follows the same contract. Named P1 candidates are alternatives, not a batch commitment.
